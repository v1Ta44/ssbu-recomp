# 不含 data.arc 的测试包与 Console 手动更新：可行性评估

实施进展：本方案中的便携更新功能现已实现，具体范围、验证和发行材料见 `PORTABLE_UPDATER_2026-10-19.md`。下文保留原评估时的事实与候选渠道边界。

核验日期：2026-10-19。评估对象：D:/pcsmash 的 yuzu 分支及现有测试包。

## 用户确认的范围

只需不包含 data.arc，目的是减少上传和下载体积。允许测试包携带现有游戏程序、重编译 DLL、系统字体等其他运行所需文件。

本方案不要求拆分游戏/SDK 派生组件，也不要求新增本机编译游戏组件的流程。首次使用者提供自己的 data.arc，其余运行文件按现有测试包方式提供。

结论：现有打包方式基本满足文件边界；免费渠道发布、Console 检测新补丁和用户手动更新均可行。后续重点是包体优化、版本协议、补丁安装与失败恢复，不需要先重构游戏/SDK 组件边界。

本文仍是评估与方案。本次没有生成新发行包、修改更新功能或对外发布。排除 data.arc 是体积要求，本文不据此作发行权利的判断。

## 现有包的实测结果

检查对象：build/dist/yuzu-all-features-20261018-98528e1.zip。

直接读取 ZIP 目录，共 75,275 个条目；没有任何文件名为 data.arc 的条目。ZIP 实际大小约 1088.7 MiB，即 1.06 GiB。

| 内容 | 压缩后约 MiB | 解压后约 MiB |
| --- | ---: | ---: |
| 游戏程序、DLL、调试文件与依赖（game） | 277.7 | 1250.1 |
| 着色器缓存（cache） | 741.1 | 2521.3 |
| 原始程序文件（binaries） | 33.6 | 94.9 |
| 字体等系统数据（sysdata） | 10.2 | 16.9 |
| Console 等根目录文件 | 4.0 | 9.5 |
| 测试资料与测试存档（tests） | 3.3 | 16.9 |
| 个人存档（userdata） | 3.3 | 16.9 |
| 其他目录 | 不足 0.1 | 不足 0.2 |

如果不附带缓存和个人/测试存档，依据现有 ZIP 条目的压缩大小相减，预计可接近 340 MiB。该数字是估算，尚未重新打包；代码、构建选项、文件增删都会影响最终体积。保留现有测试说明与输入序列即可，测试存档可按需要另行提供。

缓存适合作为可选下载内容：省去它能显著减少包体，但首次准备时间会增加。由游戏在玩家本地生成缓存。更新时保留玩家的缓存，必要的格式升级或失效处理由版本策略和运行时承担。

## 现有打包脚本可复用的能力

scripts/package.py 已提供以下选项：

- --romfs none：输出目录不加入 data.arc，其他 RomFS 文件保留。
- --zip：生成 ZIP，zip_package 也会排除标准位置 romfs/data.arc。
- --cache none：不附带着色器缓存。
- --save none：不附带作者的个人存档。
- --smoke-save none：不附带烟雾测试存档。

后续生成精简测试包可采用：

```powershell
python scripts/package.py --romfs none --cache none --save none --smoke-save none --zip
```

此命令只是方案示例，本次未运行。它仍要求当前源码、宿主程序、Console 和功能依赖已经完成匹配构建；保留现有过期构建检查，不用 --allow-stale 掩盖不一致。

玩家首次使用时，将自己的 data.arc 放入包内 romfs 文件夹，或在现有 launcher/launcher.ini 指定外部 RomFS 路径。当前 Console 已支持读取该路径。必要的 .nrr 文件继续随包保留；若指向外部 RomFS，启动前检查仍要求该目录中的 .nrr 完整。

公开包清单还应移除作者机器名、绝对路径等本机信息；现有 manifest.json 包含 packaged_on、romfs.source、symstore 等字段，适合内部追踪，不宜原样作为对外更新协议。

## 发布渠道：GitHub 主发布、大陆备用下载、离线导入

主发布保留个人 fork 的 GitHub Releases，或独立的个人发行仓库；大陆备用渠道同步同一份文件。遵循项目约定，不将个人功能合入 main，不向上游发布整套个人功能。

GitHub 官方说明：每个发行附件必须小于 2 GiB，单次发行最多 1000 个附件，发行总大小和带宽没有列出配额限制。现有约 1.06 GiB 的 ZIP 和预计约 340 MiB 的精简包都低于单附件限制。但大陆直连不能预设稳定，能打开发布页也不能代表附件或 API 可用；不能以 GitHub 为唯一更新入口。

建议发行附件：

1. 不含 data.arc、默认不带缓存和个人存档的完整测试 ZIP。
2. 带签名的版本与兼容性清单，以及版本说明。
3. 后续基于指定旧版本的文件补丁 ZIP。
4. 对应源码、构建说明和第三方授权资料。

三类入口分开管理：

- 版本清单入口：小体积签名 JSON，保留 GitHub 和至少一个经验证的大陆备用入口。清单服务也不可只依赖 GitHub。
- 直接下载入口：通过验证的 HTTPS 附件/直链，Console 可以下载，并提供来源选择和失败切换。
- 浏览器分享入口：网盘分享页。Console 只打开浏览器并说明可能需要登录、客户端或提取码，用户下载后通过“从文件更新”安装；不将分享页伪装成可直接下载的文件地址。

普通网盘账号不作为 Console 的共享登录账号，不在客户端内置发布者令牌、Cookie 或密码。对用户显示的“免费”要区分作者免费上传、接收方是否能在免费额度内下载、是否免登录，以及程序直接下载是否另收费。

### 官方信息中的具体边界

- 夸克：官方明确存在免费基础服务和付费增值服务，但本轮不采用营销文章中的速度和活动赠送容量作长期保证。[S1]

- Gitee：已核对附件下载路由和 Release 功能；未找到足够清晰、适用于当前个人社区账号的附件配额依据。因此既不把仓库的 50 MB 限制套到附件，也不把网络转载的 100 MB/1 GB 当作当前已核验结论。[S3][S4]
- AtomGit：附件下载接口文档列有 access_token 参数，需要对公开发行验证不带令牌时的真实响应；发布者凭证只能留在发布侧。[S5][S6]
- 123 云盘：官方 CDN 页面明确区分收费直链下载流量，官方会员协议也要求按对应分享/直链/开发者服务规则使用内容分发能力。普通分享与正式直链是两种候选路径，不能用破解分享页或共享账号替代正式接入。[S7][S8][S12]

### 不纳入长期免费方案的候选

腾讯云 COS 可留作未来有预算时的方案，不作为本次“长期免费”答案。其官方文档给个人新用户 50 GB、180 天的标准存储免费额度；请求和外网下行流量不在该存储赠送额度内。[S13]

没有在当前核验中确认“长期免费、无需接收方登录、可容纳完整包、可供 Console 稳定直接下载、已通过大陆多线路验证”全部同时成立的渠道。首版方案保留浏览器下载和离线导入，不以尚未验证的直链承诺大陆一键更新。

### 渠道定稿前的验证方法

先使用无游戏内容的临时测试文件，验证小清单、数十 MiB 补丁量级和约 340 MiB 完整包量级；若要保留旧大包，也验证约 1.06 GiB 量级。渠道必须按实际账号额度允许相应大小，大小不满足的只承担其适合的用途。

分别记录上传限制、免费额度与计费提示、未登录浏览器下载步骤、是否要求客户端/验证码、分享有效期、匿名 HTTPS GET 返回的是文件还是 HTML，以及下载所得哈希。直接下载候选再测重定向、断点续传、限流和链接过期；不绕过登录、验证码或付费规则。

速度和可达性在大陆电信、联通、移动实际网络上测试，记录日期、网络、文件大小、成功率及耗时。单次网页访问或当前执行环境的一次成功下载，不算全国可用验证。网盘分享页即使不能程序下载，只要人工下载步骤可接受，仍可作为离线导入备用。

发布时先构建并签名同一组附件，上传和校验各镜像，再公布版本清单；清单可以只列已同步且通过校验的来源。不因为某个候选没同步完成而挂出坏链接。

## Console 的界面和更新行为

在开始页增加版本卡片：当前测试版本、检查更新、更新说明、下载来源、下载并更新、备用网盘下载、从文件更新。直链来源可在 Console 内下载；网盘来源打开浏览器，用户下载后导入。

可以提供可关闭的启动后检查；下载和安装均由用户点击触发。检查 GitHub 失败时尝试清单备用入口；直链下载失败时提供其他直链或浏览器备用入口。网络检查需要超时和退避，不让不可用来源一直阻塞界面。

显示最后一次成功检查的时间和来源。所有入口失败时显示“暂时无法检查更新”，不能显示“已经是最新版本”；不阻止已有版本正常启动游戏。备用源返回较旧清单时不自动降级，并提示可能存在同步延迟。

建议分两步实施：

- 第一阶段：完整精简包更新。已有用户更新时，按受管理文件清单替换程序，不覆盖整个目录。
- 第二阶段：只下载变化文件的补丁包。例如只修改 Console 或宿主程序时，下载对应文件；游戏 DLL 或依赖发生变化时，将其一并纳入补丁。

第二阶段仍是完整文件替换，不做二进制差分。这样可以明显减少普通修复的下载量，也更容易核验和回滚。补丁体积取决于变动文件，不能承诺每次都很小。

## 安装流程及数据保留

1. 获取并验证版本清单，比较通道和递增版本序号，显示更新说明、体积、适用基础版本和功能组合。
2. 用户点击后下载到临时目录，检查签名、文件大小、SHA-256、归档路径及解压体积限制。
3. 检查当前受管理文件的版本与哈希。若基础版本不符或文件被本地修改，停止应用该增量包，说明原因并提供兼容的完整包更新入口，不静默覆盖本地改动。
4. 等待游戏、控制器测试等相关程序退出；更新期间阻止再次启动。其他 Console 实例和文件占用也要处理。
5. 启动可信的更新辅助程序，Console 退出；辅助程序备份旧文件，只替换或删除更新清单明确管理的文件。
6. 失败恢复旧文件并保留安装日志；成功后重新启动 Console 核对版本。多文件替换不天然具备断电原子性，需要可恢复的安装状态。

data.arc、个人存档、模组、配置、日志和报告均不属于补丁覆盖范围；缓存默认保留，必要的缓存失效通过明确的格式/版本策略处理。.nrr、ELF、游戏 DLL、依赖和启动脚本等发行文件可以在需要时更新。

目录不是简单的“保留/覆盖”二选一。例如 game 下可能存在玩家自放的模组文件，romfs 下既有 data.arc 又有发行配套文件。因此安装必须基于文件允许列表，不能先清空目录再解压。

SHA-256 用于核对文件内容，发布者身份通过预置公钥验证签名。私钥由发布者保存，签名覆盖版本、兼容信息、地址、大小及哈希；离线导入走相同验证流程。归档禁止目录穿越、绝对路径和异常链接。

## 版本协议与实现选择

当前 Console 可读取 manifest 中的 build_id，但 Console 自身 0.1.0 不能代表整包版本。建议新增公开版本清单，至少包含：

- 可读测试版本、递增版本序号、channel=yuzu-test、win-x64 平台。
- build_id、基础版本、game_version=13.0.4、所需功能组合和更新器最低版本。
- 完整包与补丁的大小、哈希、签名和下载来源列表；来源区分直接文件与浏览器分享，显示名称、提取码（如有）、同步版本和必要说明。
- 文件替换/删除列表及更新说明。

build_id 用于确认实际构建，补丁基础校验再结合文件哈希；不能只比较 Git 提交号，因为未提交修改和构建选项也会改变产物。

清单本身保留多个获取入口，并用同一公钥验证。镜像中的同一包必须有相同哈希，入口切换不能降低签名、版本和兼容性检查。优先使用已验证入口，在有限检查时长内比较收到的有效清单版本，保留已知最高序号；正常检查不得自动安装更旧版本。用户主动回退属于独立流程。

GitHub 的 /releases/latest 不返回预发行。若测试包标记 prerelease，应使用固定测试通道清单，或查询 releases 并按通道和版本筛选。匿名 REST API 当前官方主限额为每个来源 IP 每小时 60 次，检查应节流、缓存和失败退避，不轮询。

现有 Console 为 Tauri 2，已有 SHA-256、ZIP、JSON 依赖，具备界面、启动检查和进程管理。当前 bundle.active=false，为便携目录布局。Tauri 官方 updater 的 Windows 产物围绕 NSIS/MSI 安装包组织，不能直接完成当前多文件游戏目录的便携更新。建议通过 Rust 后端负责下载验证，加独立更新辅助程序完成替换。

## 建议实施顺序

1. 生成并检查不含 data.arc、默认不带缓存/个人存档的测试 ZIP，确认配置入口和发行文件清单。
2. 使用无游戏内容的测试文件验证候选渠道，先选定大陆人工下载备用，再确定签名清单备用入口；直接下载通道满足验证后才加入 Console。
3. 增加公开版本协议、测试通道、多来源清单和 Console 版本卡片，区分直接下载、浏览器下载与离线导入。
4. 实现下载验证、离线导入、退出替换及失败恢复，先支持完整包更新；清单和附件均支持来源失败后的处理。
5. 再根据两个版本的受管理文件哈希生成文件补丁，基础不匹配时退回完整包方案。
6. 在个人渠道发行并验收：首次启动、检查预发行、GitHub 不可达、备用清单不可达或滞后、网盘手动导入、损坏包、基础版本不符、运行中阻止安装、回滚、个人数据保留和实际游戏启动。

核心代码位置：scripts/package.py；tools/console/src/main.rs、game.rs、paths.rs；tools/console/ui/index.html、app.js；需要新增下载验证及更新辅助程序。
