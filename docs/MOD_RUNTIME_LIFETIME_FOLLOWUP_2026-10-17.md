## 新证据：普通池初始化不等于消费 packaged 指针

读取本机 13.0.4 的原始 `sdk.elf`，对照以下原始函数：

- packaged setter `[sdk+0x427b20]` 把指针写入 builder `+0x58`。
- texture initializer `[sdk+0x4287d0]` 复制池对象和 offset，执行布局函数 `[sdk+0x427ed0]`，普通池路径通过池虚表取得地址。
- 普通池虚表的地址点是表头之后的两个指针槽；对应方法为 `[sdk+0x42a6f0]`，没有把池构造函数误作该方法。

又用隔离的 ARM64 指令解释执行核对了初始化的实际访问路径。覆盖 512×512/0x4d/10 mip 与 128×128/0x4e/8 mip；每组分别使用 packaged=0、`0xdead00000000`、`0xbeef00000000`，后两者未映射。六组都在原函数末尾返回位置观察到 `x0=1`，同组产生完全相同的贴图对象；观察期间没有读取 builder `+0x58` 字段，池方法被调用。

证据位置为共享仓库的忽略目录：

- `build/mod-adapt/gamebanana/lifetime-followup/sdk-texture-initialize.asm`
- `sdk-pool-texture-method.asm`、`sdk-texture-layout.asm`
- `probe_sdk_texture_lifetime.py`、`sdk-texture-lifetime-result.json`
- SDK SHA-256：`d42578f463806dbd0023752dcecc43fed230c9f35d3a787696c3e92dd08eccdd`。

边界：只验证普通池、flags=0、无 GL interop 的这两组输入；池取得 GPU 地址的方法使用模型，驱动 kind 查询采用原 SDK 的失败回退路径。观察停在原函数末尾 ret 前，读取返回寄存器及对象，不执行解释器向宿主返回与清理。没有把这项检查宣称为完整 NVN 接口规范或实际 GPU 运行。

因此，上一轮不能继续把“原接口要求消费临时 packaged 输入，所以复制便完成修复”当作既定前提。当前运行时把 `b.packaged` 同时用于源选择与仅上传一次的判定，这需要与普通池的所有权分别审查。

## 旧现场进一步排除了什么

第二轮转储中 `b.packaged == t->mem == 0x21c8ceaf000`。仅把读取字段从 packaged 改成池地址，仍会读取同一个地址，解释不了原异常。

本轮再次扫描小转储的全部捕获内存：池对象地址 `0x21c50a14e00` 和源地址都不在捕获范围，未发现对应池登记的关键字段组合，也没有 FullMemoryInfo 流。结果在 `old-dump-owner-search.json`。所以仍不能凭这份小转储断言池已销毁、页面已撤销提交或指针遭破坏。

现在应优先补证的具体链条是：池初始化的一代资源 → 贴图绑定这代池 → CPU 读取开始/结束 → 池销毁开始/结束 → 页面释放成功/失败 → 同地址池重新初始化 → 旧贴图是否再次读取。

## 独立取证实现

新增 `runtime/nvn_lifetime.c/.h`，默认关闭。通过 `SSBU_NVN_LIFETIME=<新日志路径>` 启用；不改 Tex 布局，不改变副本所有权、资源销毁条件或 GPU 同步策略。事件写入固定 80 字节记录，包含严格序号、QPC、线程、宿主贴图身份、游戏对象、池地址、实际源范围、调用位置。记录器自身不使用 malloc/free。

钩子位于：

- `nvn_gl.c`：初始化、packaged 原源、副本取得/释放、初始化失败、finalize、两条哈希路径及逐 mip 解 swizzle 的实际 CPU 读取区间。
- `nvn_stub.c`：池初始化及 finalize 开始/结束。
- `nnsdk.c`、`nnsdk2.c`：页面释放、整块释放以及 keep 模式的逻辑释放；记录真实释放结果。整块释放的 size=0 在操作前解析分配范围，仅启用取证时执行。
- `tools/lifter/build.py`：只接入宿主记录器源文件。

`scripts/analyze_nvn_lifetime.py` 分别识别成功释放与读取区间重叠、释放后的借用读取、旧池销毁后的借用读取、同地址池换代后旧贴图继续读取，以及宿主副本释放后的读取。拥有的副本与借用源分别处理；失败的释放不记为内存已失效。池 finalize 的开始/结束绑定到开始时的那一代池，避免新池在旧 finalize 尾部日志前初始化时被错误判定为已销毁。

`scripts/play_resource_test.py --lifetime-trace` 是显式选项，会把日志放在对应测试会话下，并在退出后生成 `nvn-lifetime-analysis.json`。本轮已与经过验证的宿主源码整合，诊断入口为第四项另设目录；原测试 EXE 未覆盖，也不要求回测已通过的 2、3 号。

## 验证与限制

只保留一个原生记录/分析契约检查 `tests/test_nvn_lifetime_trace.py`。它不加载游戏 DLL、不启动 GPU：真实跨线程释放覆盖记录中的读取区间，再在同一地址重新分配；校验新旧池身份、副本独立性、失败释放排除、旧 finalize 尾部与新初始化交错，以及崩溃留下不完整日志尾部的解析。

这是合成的事件/分析检查。标记的读取没有真的解引用已释放内存，不能冒充原游戏崩溃复现。原生检查通过；四个宿主钩子文件通过实际工具链语法检查；启动器 `--lifetime-trace --describe` 通过只读检查，未创建游戏会话。

取证日志只代表已记录的前缀，缺少事件不能证明没有发生释放。操作区间相交说明存在生命周期风险，仍需异常现场才能确定失败指令的先后。游戏分配器在没有可见池换代/页面事件时的内部复用尚未跟踪；线性贴图的全部上传/读回回调也未覆盖。记录会影响线程时序和 I/O，不作为性能基准。

本补丁提供可核验事件链，不宣称已经修复第二轮贴图崩溃。下一步依据真实事件确认是旧池引用、地址换代、读取越过退役，还是另一条未观测到的源失效路径，再决定最小的所有权/退役修复。保留已有计算回写退役修复；合并时不能用本工作树的基线文件覆盖其他任务的新代码。

源码核查明确了下一步边界：

- 并行修复后的 Vulkan 池 finalize 通过同步 `gl_run(nvn_vk_memory_retire, ...)` 等待渲染任务，不能笼统说此路径只检查 `g_async_pending`。退役函数主要处理计算缓冲区，也不能由此推出所有未来贴图借用都已经登记失效。
- Vulkan 普通贴图上传的 `vt_put` 同步把输入复制到上传环；后续 GPU 命令引用上传环。CPU 读取结束与 GPU 执行结束是不同边界，不能仅凭副本在 GPU 完成前释放就判错。
- 页面日志没有覆盖 `SetMemoryPermission` 的权限切换，也看不到游戏 jemalloc 在已提交页面内的全部子块回收。`nu::VirtualFreeHook` 是游戏自身 free 之前的通知，不能直接当成页面释放完成。线性贴图回调尚未全部埋点。这些是取证边界，当前没有证据要求修改它们的运行行为。
