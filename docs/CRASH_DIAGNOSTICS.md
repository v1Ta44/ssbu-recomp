用户手动尝试也未成功复现，按用户要求结束本轮排查，不再继续安排复现测试。状态是“未稳定复现，根因未确定”，不是“已修复”。预热优化和独立诊断入口保留，日常使用普通启动入口即可；再次出现同类异常时，再根据新证据重开调查。

原崩溃日志、小转储、匹配程序快照、复现结果及用户本次诊断目录均保留。为验证转储功能而故意制造的约 2.45 GB 完整转储在收尾时清理，生成日志、大小、FullMemory 标志和通过结果保留。验证中的程序哈希仅指当时的快照，不代表之后其他工作更新的当前主程序。

双击项目根目录 `YuzuDiagnose.bat`，按平时的步骤连接房间、开始游戏。它运行单独的 `build/work/ssbu_diagnostic.exe`；普通 `YuzuPlay.bat` 继续使用原来的 `ssbu_native.exe`。也可运行：

```powershell
.venv/Scripts/python.exe scripts/yuzu_play.py --diagnostic
```

诊断版使用与平时相同的 `build/userdata_yuzu` 存档。启动前先保存已提交存档的副本。每次在 `build/logs/yuzu-diagnostic-日期-时间/` 建立独立目录，保存：

- `game.log`、`boot_trace.txt`：本次运行日志。
- `pads.csv`：所有玩家最终收到的按键、左右摇杆、连接状态，按变化记录，包含相对时间和各玩家轮询编号。
- `input.rec`：旧的玩家 1 回放格式；它不包含其他玩家和右摇杆。`pads.csv` 是诊断记录，不能直接交给 `SSBU_PLAY` 回放。
- `userdata_before/`、`config_before/`：启动前已提交的存档／缓存及画面、控制器设置。
- `binaries/`、`manifest.json`：本次 EXE、PDB、MAP、游戏主 DLL 副本及 SHA-256，用于匹配转储。
- `process.json`：本次进程编号。
- 崩溃时的 `*_crash.txt`、`*.dmp`：完整进程转储。没有崩溃时不会产生崩溃转储。

完整转储可能有数 GB，写入完成前需要等待。诊断入口不会设置自动故意崩溃、跳过影片、自动按键或提前结束游戏。

## 2026-10-15 的验证

- 原崩溃加载特瑞（dolly）和露琪娜（lucina）。当时物理手柄分配到玩家 2，而旧录制器只记录玩家 1；这解释了只有空输入的一份 `input_last.rec`，不能把它当作原操作回放。
- 使用原 EXE 字节相同的测试副本和独立全解锁存档，在终点做特瑞对露琪娜、3 级 CPU、99 条命、正常速度的自动动作测试。完成 10800 个战斗帧（约 3 分钟），进程 239.667 秒、退出码 0，无 HOST EXCEPTION。原场地、操作未知，因此不是原局精确复现，也不能证明问题消失。首轮停在开场影片，已作为无效复现单独保留。
- 新增输入观察器只在 `SSBU_PAD_TRACE` 指定时输出，不改写控制器状态。原生测试覆盖玩家 2、玩家 8、双摇杆、变化去重、断开状态及输入未改变。
- 启动器的 2 项自动测试通过：诊断参数／证据独立保存，普通启动保持原模式。
- 独立的故意崩溃自测成功写出完整转储：2448532624 字节（约 2.45 GB），检查到 FullMemory 标志，退出码 4 符合自测预期。该自测位于 `work/crash-20261015-200833/dump-selftest/`，不是再次复现用户的原崩溃。
